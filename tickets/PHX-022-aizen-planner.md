# PHX-022 — AIZEN Planner

Status: DONE
Phase: 2 — Orchestration

## Objective

Implement the first provider-neutral AIZEN planning boundary for complex PHOENIX work.

AIZEN is the chief strategist/master planner. PHOENIX remains the sole supreme
orchestrator and final user-facing completion authority.

PHX-022 must establish:

- authoritative planner identity through neutral internal ID `strategist`
- immutable planning request, subordinate draft, step, and finalized-plan contracts
- a provider-neutral async planning collaborator boundary
- validation/finalization of a bounded structured decomposition
- request-scoped active planning tracking
- duplicate-plan-request protection
- request-scoped cancellation and deterministic cleanup
- explicit separation from routing, task execution, task state, handoffs,
  verification, recovery, permissions, tools, persistence, events, and providers

This ticket does **not** wire AIZEN into the PHOENIX orchestrator yet. PHX-021
continues to return `planning_required` for complex work until later orchestration
integration is deliberately implemented.

## Frozen identity

Planner internal ID:

`strategist`

Display alias:

`AIZEN`

The internal ID is authoritative. The alias is display metadata only.

Changing or removing the AIZEN alias must not change planner authority or runtime
behavior.

PHOENIX remains the only supreme orchestrator.

AIZEN may plan/decompose complex work. AIZEN may not:

- independently finalize user-facing success
- grant permission
- execute tools
- become the supreme orchestrator
- bypass LEVI verification
- invoke MAHORAGA recovery policy
- enter KAIDO degraded mode

## Implementation boundary

Prefer a small module under:

`phoenix/agents/planner.py`

Likely public concepts:

- `PlanningRequest`

- `PlanDraft`
- `PlanningResponder`
- `AizenPlan`

Exact naming may differ if the resulting design is smaller and clearer.

Do not create one runtime class per agent.

Do not add workflow frameworks.

## Planning request

Provide an immutable validated planning request.

Minimum fields:

- `request_id`
- `objective`

`request_id`:

- generated by default or caller-preserved
- strict nonempty normalized identifier
- serializable
- stable for the entire planning operation

`objective`:

- strict string
- must contain non-whitespace content
- preserve meaningful caller whitespace/content
- never automatically logged

Do not add provider/model fields.

Do not add permission grants.

## Plan step

Provide a minimal immutable planning-step proposal.

Minimum fields:

- `step_id`
- `objective`

`step_id` is a planning-local stable identifier only.

It is **not** yet:

- a PHX-024 runtime task-step state object
- a PHX-025 handoff envelope
- an agent assignment
- a model assignment
- a tool call

Steps must preserve the responder-supplied order.

Step IDs must be unique within one plan.

Step objectives must be meaningful nonempty text.

Do not add execution state.

Do not add dependencies/graph edges in PHX-022 unless existing authority makes them
strictly necessary. PHX-024 owns task graph/state-machine semantics.

## Plan draft

`PlanDraft` is subordinate collaborator output.

Minimum:

- correlated `request_id`
- ordered immutable nonempty tuple of `PlanStep`

Requirements:

- request ID must correlate with the planning request
- at least one step
- unique step IDs
- exact order retained
- extra fields forbidden
- no arbitrary metadata dictionary
- no raw model/provider response object

A draft is not PHOENIX completion and not yet executable task state.

## Planning responder

Define a minimal provider-neutral async collaborator boundary, conceptually:

```python
class PlanningResponder(Protocol):
    async def propose(self, request: PlanningRequest) -> PlanDraft:
        ...
```

Equivalent naming is acceptable.

The contract must not expose:

- Ollama
- Colibri
- HTTPX
- `ModelProvider`
- model IDs
- provider IDs
- model tiers
- lifecycle internals
- tools
- permissions

Tests must use fake responders.

No production fake responder.

## Finalized AIZEN plan

Provide an immutable finalized plan value.

Minimum:

- `request_id`
- authoritative `planner_id = "strategist"`
- ordered tuple of validated plan steps

A finalized AIZEN plan means only:

> AIZEN produced a validated decomposition proposal.

It does **not** mean:

- PHOENIX completed the user request
- steps were routed
- a task graph exists
- any specialist ran
- any model/tool action succeeded
- verification passed

AIZEN must never emit `PhoenixResult(kind=completed)`.

## AizenPlanner

Construction must validate that the supplied/default `AgentRegistry` contains the
authoritative neutral internal ID:

`strategist`

Do not establish planner authority through alias `AIZEN`.

Alias rename/removal must not change behavior.

The planner should expose one obvious async planning entry point such as:

`await planner.plan(request, responder=...)`

Exact signature may differ if clearer.

Planner flow:

1. validate request and authoritative identity
2. register request as active
3. call the injected `PlanningResponder` exactly once
4. validate draft type/shape/correlation/step uniqueness
5. revalidate immutable public values
6. finalize as `AizenPlan(planner_id="strategist")`
7. remove active state in `finally`

No model selection occurs here.

## Correlation

The planner must reject a draft whose `request_id` differs from the active
`PlanningRequest.request_id`.

Do not silently rewrite collaborator correlation.

## Strict subordinate boundary

A collaborator must not be able to smuggle final authority through subclasses or
arbitrary extended public models.

Revalidate subordinate output into the exact neutral contract before finalization.

Malformed output must fail explicitly.

Do not fabricate a plan after collaborator failure.

## Active planning tracking

Track active planning request IDs in memory on one process/event loop.

Requirements:

- active before awaiting responder
- removed after every terminal path
- distinct request IDs may be active concurrently
- same request ID cannot be active twice
- no mutable internal task map exposed publicly
- deterministic immutable active-ID inspection

Do not persist active plans.

## Duplicate request behavior

Simultaneous duplicate `request_id` must fail explicitly before replacing active
state.

A small `DuplicatePlanningRequestError` or equivalent is acceptable.

After cleanup, the ID may be reused.

## Caller-task ownership

PHX-021 established caller-task ownership for request-scoped cooperative
cancellation. PHX-022 may use the same narrow pattern.

If one caller task would own multiple simultaneous active planning requests on the
same planner, reject that arrangement if necessary to preserve cancellation
isolation.

Do not create hidden worker tasks just to support cancellation.

## Cancellation

Expose request-scoped cancellation.

Minimum statuses:

- `accepted`
- `not_found`

Cancellation of planning request A must not cancel planning request B.

Accepted means local cancellation was requested. It does not prove remote model
computation stopped.

Do not swallow `asyncio.CancelledError`.

If a responder suppresses cancellation, it must not be allowed to finalize a
successful AIZEN plan after the planner has recorded cancellation.

## Cleanup

Use `try/finally`.

Active state must be removed after:

- successful planning
- responder exception
- invalid/malformed draft
- request-ID mismatch
- duplicate/correlation error after registration where applicable
- caller cancellation
- planner cancellation

No stale active IDs.

## Failure semantics

Use a small explicit planner error boundary if useful, e.g.:

- `AizenPlanningError`
- `DuplicatePlanningRequestError`

Avoid a large hierarchy.

Responder failures remain failures.

Do not convert exceptions into valid plans.
