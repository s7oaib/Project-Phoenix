PHOENIX remains the only component that may produce a normal user-facing orchestration completion result.

## Frozen architecture to preserve

- PHOENIX is the single supreme orchestrator.
- User normally talks to PHOENIX, not an agent chat room.
- Simple requests may stay inside PHOENIX.
- Complex requests may later be decomposed by AIZEN.
- AIZEN plans but never becomes final orchestration authority.
- Agent/model routing belongs to PHX-023.
- Task lifecycle/state machine belongs to PHX-024.
- Structured handoffs belong to PHX-025.
- LEVI runtime verification belongs to PHX-026.
- MAHORAGA bounded recovery belongs to PHX-027.
- KAIDO degraded fail-safe belongs to PHX-028.
- PermissionEngine remains deterministic authority; PHX-021 grants no permission.
- Tools remain behind ToolRegistry; PHX-021 executes no tools.
- Provider-specific implementation never leaks into the orchestrator contract.

## Implementation scope

Implement a small orchestration module under `phoenix/agents/`, preferably `phoenix/agents/orchestrator.py`.

The implementation should provide:

- immutable validated user-request contract
- explicit direct-vs-complex orchestration directive/path metadata
- testable provider-neutral direct-response collaborator boundary
- immutable PHOENIX result contract
- PHOENIX-owned finalization for successful direct responses
- explicit `planning_required` result for complex work until PHX-022 exists
- request-scoped active-operation tracking
- duplicate active request protection
- operation-scoped cancellation
- deterministic read-only active-request inspection
- strict cleanup after success, failure, cancellation, and complex-path return
- integration with PHX-020 `AgentRegistry` only for authoritative PHOENIX identity validation

Do not add speculative service/repository/controller layers.

## PHOENIX identity

The orchestrator must bind to authoritative internal ID:

`phoenix`

It must not depend on alias text `PHOENIX` for behavior.

Construction must validate that the supplied/default agent registry contains the authoritative PHOENIX definition and that no other identity is treated as supreme orchestration authority.

Alias removal/renaming must not affect orchestrator behavior.

## Request contract

Create an immutable validated request model with the smallest useful fields.

At minimum:

- `request_id`: generated by default, caller-preservable, nonempty, serializable
- `text`: strict nonempty user text

An optional neutral input-channel/modality field such as `text` / `voice` is acceptable as descriptive metadata only if kept small and provider-independent.

Do not include:

- provider objects
- model IDs
- tool objects
- permission grants
- task-graph state
- database handles
- agent aliases as authority

## Orchestration path/directive

Represent only the high-level path required by current architecture:

- `direct`
- `complex`

This is not PHX-023 routing.

PHX-021 does not classify domain specialists, providers, models, tools, or risk. The path/directive is supplied explicitly by the caller/test boundary until later routing/decision logic is implemented.

`direct` means PHOENIX may use the injected direct-response collaborator.

`complex` means return an explicit `planning_required` PHOENIX result. Do not call AIZEN because PHX-022 does not exist yet.

Do not silently treat complex work as completed.

## Direct-response collaborator boundary

Define a small provider-neutral async protocol/ABC for direct PHOENIX responses, for example conceptually:

`async respond(request) -> DirectResponse`

The production contract must not import or instantiate Ollama/Colibri.

The collaborator may later be backed by model routing/runtime, but PHX-021 must not select a provider/model itself.

Use test-only deterministic fake responders.

The direct response contract must preserve request identity and contain user-facing text only; no arbitrary raw provider metadata.

## PHOENIX result contract

Return an immutable validated PHOENIX-owned result.

Minimum semantics:

- request identity preserved
- authoritative source/orchestrator internal ID is `phoenix`
- result kind distinguishes at least:
  - `completed`
  - `planning_required`
- completed results contain nonempty user-facing text
- planning-required results must not falsely contain a successful completion

Provider/collaborator failures must remain exceptions/failures, not fabricated completed results.

Do not create the PHX-024 task-state machine in this ticket.

## Finalization authority

Only `PhoenixOrchestrator` should construct/return normal PHOENIX orchestration completion results in this module.

The direct responder returns a subordinate direct-response value, not the final supreme-orchestrator result.

AIZEN/LEVI/other agents do not exist as runtime collaborators in PHX-021.

## Active request tracking

Track active `request_id` values only in memory for one process/event loop.

Requirements:

- no background workers
- no hidden tasks
- no persistent state
- duplicate simultaneous `request_id` rejected explicitly
- different request IDs may be active concurrently
- active state removed after every terminal path
- read-only inspection such as `active_request_ids` or equivalent returns immutable deterministic evidence

Do not expose mutable task dictionaries.

## Cancellation

Provide operation/request-scoped cancellation.

A compact explicit outcome such as:

- `accepted`
- `not_found`

is sufficient.

Cancellation must:

- affect only the matching active request
- not cancel unrelated requests
- not shut down providers globally
- not kill processes
- not unload models
- not swallow normal `asyncio.CancelledError`

The orchestrator may cancel the caller task associated with the active `handle/execute` operation, analogous to existing provider cancellation patterns.

No hidden task should be created solely for cancellation.

## Duplicate request handling

A second simultaneous orchestration operation with an already-active `request_id` must fail explicitly before corrupting state.

After the original request is cleaned up, the same ID may be reused.

## Failure and cleanup

Use `try/finally` so active-request state is removed after:

- direct success
- direct collaborator failure
- caller cancellation
- orchestrator cancellation
- validation/protocol failure
- complex/planning-required return

Do not convert failure into success.

A small orchestrator-specific exception boundary is acceptable, e.g. `PhoenixOrchestrationError` / `DuplicateRequestError`.

Avoid a large speculative hierarchy.

## Registry integration

Use the PHX-020 neutral registry only to establish PHOENIX identity.

Do not:

- mutate the registry
- route by registry role
- infer permissions from role text
- search aliases for authority
- mark agents online
- create one process/model per registry entry

- call a provider
- run inference

- start threads

Only an explicit orchestration call may await the injected direct responder.
